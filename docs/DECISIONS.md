# DECISIONS

Format: `[D-NN] <decision> | why | rejected: <alternatives>`

Every non-trivial choice not explicitly fixed by the master prompt lands here. Decisions are append-only; if one is later reversed, the reversal is a new entry that references the old one.

## Money & pricing

**[D-01] All monetary amounts are stored as `bigint` agorot; no floats, anywhere, ever.** | Floating point cannot represent decimal currency exactly. A 20% commission taken from a float price produces sub-agora drift that compounds across the payout ledger and eventually shows as a real reconciliation gap. `bigint` also survives a future currency with different minor units. | rejected: `numeric(12,2)` (correct arithmetic, but invites accidental float coercion through the JS client, which has no decimal type — every read would come back as a JS number anyway); float/double (unsafe); storing formatted strings (unsortable, unfilterable).

**[D-07] The floor surcharge is evaluated independently per side (pickup and dropoff); each side charges `floor_surcharge_agorot` when floor ≥ 3 AND that side has no elevator.** | The master prompt says "+₪50 per side where floor ≥ 3 without elevator" but does not name the sides. The crew carries the item down at pickup and up at dropoff — those are physically separate efforts, so a 4th-floor walk-up on both ends is genuinely twice the work and charges ₪100. Floors 0–2 never surcharge; an elevator suppresses that side's surcharge at any floor. | rejected: single surcharge for the whole order (under-recovers on the common both-ends-walk-up case); charging by floor count (opaque to the buyer at checkout, and the crew cost is a step function, not linear).

**[D-08] Self-pickup zeroes the delivery fee AND both floor surcharges AND the disassembly surcharge — a self-pickup order's total is the item price alone.** | Every one of those charges exists to pay a crew. On self-pickup there is no crew: the platform performs no carrying and no disassembly. Charging a disassembly fee for work the platform does not do would be indefensible at the first support ticket. | rejected: keeping disassembly on self-pickup (platform isn't doing it); keeping a reduced "handling" fee (invents a charge the spec doesn't authorise).

**[D-09] Commission is computed on the item price actually paid, not the original asking price.** | When an offer is accepted the transaction price *is* the offer amount; taking 20% of a higher asking price would silently raise the effective commission rate on every negotiated sale (a ₪1000 ask sold at ₪600 would be taxed 33%). | rejected: commission on asking price (punishes sellers for negotiating, exactly the wrong incentive for a marketplace whose supply is scarce).

**[D-10] Commission rounds down: `floor(item_agorot * commission_pct / 100)`; the seller payout is `item_agorot − commission_agorot`.** | Rounding must never create money out of nothing, and the residual agora should favour the party the platform is trying to attract. Deriving payout by subtraction rather than by its own rounded formula guarantees `commission + payout == item` exactly, which is what the payout ledger reconciles against. | rejected: round-half-up (can round the platform's take above the stated 20% on some amounts); computing payout independently with its own rounding (the two can disagree by an agora and break reconciliation).

**[D-18] `computeOrderPricing()` is a pure function with no I/O, taking `(listing, deliveryDetails, config)` and returning the full breakdown; it is the single source of truth used by the checkout UI, server-side validation, and admin.** | Fee logic duplicated between client and server is the classic marketplace bug: the buyer sees one total, the server charges another. One pure function is trivially unit-testable and cannot drift from itself. | rejected: computing fees in SQL (untestable in isolation, unavailable to the client-side estimator); computing in the UI and trusting it server-side (lets a crafted request set its own delivery fee to zero).

**[D-19] Server-side checkout re-computes the price from scratch and rejects the request if the client-submitted total disagrees.** | The client total is a display artefact, never an input. Re-computation is the only defence against a tampered checkout payload. | rejected: trusting the submitted total; signing the quote client-side (a signature proves the quote wasn't edited, not that it was ever correct).

## Data model & database

**[D-02] `categories` and `brands` are tables with slugs, not free-text columns on `listings`.** | `/category/[slug]` and `/brand/[slug]` are core SEO surfaces (master prompt §6) and cannot be generated from free text without duplicate/misspelt variants fragmenting them. Hebrew makes this worse: ספה/ספות/סַפָּה would each become a separate "category". | rejected: free-text with normalisation at query time (normalisation rules become a second, worse schema); an enum column (adding a category would require a migration, and Tom must be able to do it from admin).

**[D-03] Listing photos live in a child table with an explicit `sort` column, not an array column on `listings`.** | Cover-photo selection, drag-reordering, and per-photo AI-generated Hebrew `alt_text` each need an addressable row. An array of URLs supports none of them without rewriting the whole array on every change. | rejected: `text[]` of storage paths (loses alt text and stable identity per photo); JSONB array (same, plus no FK integrity to storage cleanup).

**[D-04] Order and listing status transitions are enforced by a single SQL transition function plus CHECK constraints — illegal transitions are impossible at the database layer, not merely discouraged in application code.** | The order status is a claim about where real money and a real sofa currently are. Any path that can corrupt it — a retried webhook, a double-clicked admin button, a future script, a direct SQL fix at 2am — must be blocked by the database, because the database is the only layer every path goes through. | rejected: application-layer guards only (bypassed by any direct DB access, and there will be direct DB access); DB triggers scattered per-table (transition rules end up in several places and drift); no enforcement (the failure mode is paying a seller for an undelivered item).

**[D-05] `order_events` is append-only: inserts allowed, updates and deletes revoked at the table level.** | The audit trail's only value is that it cannot be edited after the fact. A mutable audit log is a log, not an audit. This is what makes a disputed refund reconstructable months later. | rejected: mutable events table (worthless in a dispute); relying on Postgres WAL/PITR (not queryable by the app, and gone after the retention window); logging to an external service (adds a dependency to the money path).

**[D-06] `pickup_street` is a separate column from `pickup_city`, is never selected by any public query, and is exposed by RLS only to the seller, an admin, or the buyer of a paid order.** | The single most likely privacy defect inherited from a classifieds-shaped schema is rendering a full home address on a public item page. Splitting the column makes the safe query the *natural* one — a public `select` that forgets to exclude the address cannot accidentally include it, because the address is not in the public projection at all. Structure beats vigilance. | rejected: one `address` column filtered in the UI (one forgotten `select *` leaks every seller's home address); filtering only in RLS (correct, but a service-role query bypasses RLS — the column split protects those too).

**[D-22] User references are `uuid` FKs to `auth.users`, and the legacy import resolves legacy email-based references to uuids, tolerating unresolvable ones by creating placeholder profiles.** | Base44 stamps `created_by` with the user's *email*. Email as a foreign key breaks the moment a user changes address, and copies PII into every child row. Placeholder profiles (rather than a hard failure) keep the import non-fatal for sellers who no longer exist, which is the realistic case for a year-old marketplace. | rejected: keeping email FKs (PII sprawl, breaks on email change); failing the import on unresolvable users (guarantees the migration never completes).

**[D-23] `updated_at` is maintained by a shared trigger function on every mutable table, not by application code.** | Application-set timestamps are missed by admin SQL, cron jobs, and any future service. | rejected: app-layer timestamps; `DEFAULT now()` only (never updates).

**[D-24] Slug uniqueness is guaranteed by a 6-character suffix derived from the listing id, not by a uniqueness retry loop.** | Two sellers listing "ספה תלת מושבית איקאה" on the same day is the expected case, not an edge case. A deterministic suffix makes the slug collision-free by construction and stable for the item's lifetime — which matters because the URL is the SEO asset and must never change. | rejected: retry-with-counter on collision (racy under concurrency, and produces ugly `-2`/`-3` URLs); full uuid in the slug (hurts readability and CTR); slug from title alone (collides immediately).


**[D-17] Every fee, window, threshold and percentage lives in `site_config` as a typed `jsonb` row with a description, read at request time — no money constant is a literal in application code.** | The legacy app hardcoded fees across at least four files with values that contradicted each other, so "what is the commission" had four answers and changing it meant a deploy. One keyed table makes the answer singular, editable from `/admin/config` by someone who does not write TypeScript, and self-documenting — each row carries the sentence explaining what it governs, which is what turns the table into the place people look. `jsonb` rather than `text` so a tier list (`commission_tiers`) and a scalar (`commission_pct`) live in the same column without a second table. Defaults ship in `0013_config_defaults.sql`, so a freshly migrated database prices correctly before anyone opens the admin. `is_public` is on the row rather than a separate table because exactly one key (`admin_email`) is not world-readable, and the read policy on `site_config` filters on it. | rejected: constants in a TypeScript module (a deploy per price change, and the legacy failure mode was precisely that these drift apart); environment variables (untyped, undocumented, invisible to the admin UI, and a restart per change); a column-per-setting table (every new setting is a migration).

## Transactions & lifecycle

**[D-11] A buyer may cancel any time before `picked_up`; from `picked_up` onward the only route out is a dispute.** | Cancellation is free to the platform only while no crew has been dispatched and no item has been handled. Once the crew has the sofa in the van, "cancel" is not a state change, it is a logistics problem with a cost attached — which is what the dispute flow exists to adjudicate. | rejected: cancel allowed until `delivered` (the platform eats the round-trip haul with no recourse); no buyer cancellation at all (traps buyers in orders sellers are slow to confirm, and invites chargebacks).

**[D-12] A pickup inspection mismatch is an admin-initiated cancel with full refund, available from `delivery_scheduled` and `picked_up`.** | The inspection is the mechanism that makes buyer protection real rather than a marketing claim. The crew is the platform's eyes; when the item doesn't match the listing the platform must be able to stop the transaction *before* it becomes the buyer's problem. Full (not partial) refund at this stage because the buyer has received nothing. | rejected: proceeding to delivery and letting the buyer dispute (ships a known-bad item, burns the delivery cost, and spends the trust the whole model is built on); partial refund (buyer received nothing).

**[D-13] `disputed` is reachable only from `delivered`, and only while the protection window is open.** | A dispute is a claim that the delivered item is not as described — it is meaningless before delivery, and the window is the promise being made to the buyer. Enforcing the window in the transition function rather than the UI means a late dispute cannot be filed by a crafted request. | rejected: disputes from any state (overlaps cancellation and makes the state machine ambiguous); open-ended dispute window (sellers can never be paid with certainty).

**[D-14] The seller *proposes* 2–3 pickup windows; the platform *schedules*. There is no user-facing delivery-scheduling page.** | The legacy `ScheduleDelivery` route implies the user picks a slot, which is only sound if slots are backed by known crew capacity. They aren't — capacity is Tom's crews, and only admin knows their load. Letting sellers self-schedule would produce a calendar the platform cannot honour, and the first broken pickup appointment costs more trust than the convenience gains. | rejected: seller picks a real slot from live capacity (requires a crew-capacity model and a crew app — explicitly out of scope, §10); admin schedules with no seller input (guarantees pickup windows the seller isn't home for).

**[D-15] Offers are built in full, including one counter round, 72h expiry, and a 24h exclusive checkout link at the accepted price — while the listing stays purchasable at full price by others until the offer-holder checks out (first capture wins).** | Negotiation is the behaviour Yad2 and Facebook Marketplace have trained Israeli second-hand buyers to expect; a fixed-price-only marketplace reads as more expensive even when it isn't. Keeping the listing live during the exclusive window prevents a lowball offer from taking scarce supply off the market for a day at no cost to the offerer. | rejected: no offers (loses the conversion mechanic); unlimited counter rounds (turns into chat, which is out of scope, and delays scarce supply); reserving the listing on offer acceptance (lets any buyer freeze inventory for free).

**[D-20] Auto-cancel, auto-complete, and expiry run as idempotent cron routes guarded by a `CRON_SECRET` bearer token, and every timer is evaluated from a DB timestamp rather than a scheduled job's own clock.** | Cron delivery is at-least-once and sometimes late; a timer that fires twice must not refund twice. Deriving "is this order past its 48h window" from `confirmed_at` in the database makes every run idempotent by construction and makes a missed run self-healing on the next tick. | rejected: per-order scheduled jobs (each one is a thing that can be lost, and the schedule becomes state to maintain); trusting invocation time (a late cron silently skips orders); no auth on cron routes (a public endpoint that cancels orders and issues refunds).

**[D-21] Payment capture is immediate at checkout at MVP, behind a `capture_mode` config key defaulting to `'immediate'`.** | Fixed by master prompt §3.3. Recorded here because the config key is the seam that lets authorize-then-capture (J5/J2) arrive later without a schema change. | rejected: authorize-then-capture now (PSP-dependent and explicitly deferred by the spec).


**[D-16] Seller payouts are a first-class ledger table with one row per order, created on completion and marked paid by an admin — not fields on `orders`.** | The legacy database had no payout table at all and one payout on record, which means "have we paid this seller" was unanswerable from the data. A ledger makes it a query. One row per order (`order_id` is `unique`) rather than per period, because the amount is derived from a single order's pricing `[D-10]` and reconciling a batch back to its orders after the fact is the work the unique constraint removes. The row is created when the order completes and starts `pending`; an admin marks it `paid` with a `method_note`, and a CHECK constraint refuses `paid` without a `paid_at`, so the ledger cannot record a payment with no date. Both the seller and the admin read the same rows — the seller sees their own by RLS — so there is no second, private view of what is owed. | rejected: `payout_status` and `paid_at` columns on `orders` (no room for a method note or a payment reference, and it overloads a table whose lifecycle is already the most constrained thing in the schema); generating payouts on demand from completed orders (a report, not a record — it cannot represent a payment that was made, and it silently changes when historical pricing config changes); batching payouts per seller per period (an aggregation the MVP has no volume to need, bought at the cost of order-level traceability).

## Architecture & infrastructure

**[D-25] The app talks to Postgres exclusively through `@supabase/supabase-js` (PostgREST), with a typed repository layer in `src/lib/db/` between the app and the client.** | Keeps the production path exactly as specified while giving one place to enforce the safe projections from `[D-06]` and to keep query shapes testable. | rejected: a second `pg`-based driver for local dev (two implementations of every query is guaranteed drift, and the drifted one is the one that isn't tested); an ORM (explicitly rejected by the master prompt §4).

**[D-26] Local development and tests in this sandbox run against a self-assembled Supabase-compatible stack — local PostgreSQL 16 + the real PostgREST binary + a minimal auth/storage shim — rather than against the remote Supabase project.** | The session's egress policy blocks `*.supabase.co` (verified: proxy returns 403 to CONNECT for `vntihvctqueohwprafwh.supabase.co:443`), so the app cannot reach the remote project from this sandbox at runtime. Using the *real* PostgREST binary rather than a fake API means RLS is genuinely enforced end-to-end in tests — which is the single most valuable property to verify, since RLS is what stands between a curious buyer and every seller's home address. Migrations are still applied to the remote project out-of-band via the Supabase MCP, so remote and local converge on identical schema. | rejected: mocking the database in tests (would never have caught an RLS mistake, which is the defect class that actually matters here); dual `pg`/`supabase` drivers (see `[D-25]`); skipping local verification and shipping unverified (fails the run's definition of success); `supabase start` via Docker (no Docker daemon in this sandbox).

**[D-27] Third-party services (payments, email, AI) sit behind narrow interfaces with mock implementations selected by env var; the mock is the default.** | Fixed by master prompt §4 (§8 of the operating protocol). Recorded because it has a consequence worth stating: the entire purchase lifecycle is e2e-testable with zero credentials, which is what makes Gate 6's clean-clone test meaningful. | rejected: calling real services in tests (flaky, costs money, needs secrets in CI).

**[D-28] Authorization is checked explicitly in every server action and route handler; RLS is the backstop, not the only check.** | Fixed by master prompt §4. Consequence: any query made with the service-role key bypasses RLS entirely, so service-role usage is confined to a small, audited set of admin/cron paths that do their own role checks. | rejected: relying on RLS alone (service-role paths would be unguarded).

**[D-29] `ADMIN_EMAIL` defaults to the repository owner's git email (`tom@gteveryday.com`) and admin is granted by matching it at profile-creation time.** | The master prompt's §9 leaves `ADMIN_EMAIL` blank and instructs the Phase 1 default to be the repo owner's git email. Bootstrapping from an env var rather than a hardcoded uuid means the same migration works on a fresh database in any environment. | rejected: hardcoding an admin uuid (breaks on every fresh database); a first-user-is-admin rule (whoever signs up first on production becomes admin — an obvious hole).

**[D-30] Google OAuth is configured for production but is not exercised by the local e2e suite; the suite authenticates via email+password against the local auth shim.** | Google's consent flow cannot be driven headlessly without real credentials and a real redirect origin, and a test that depends on Google's uptime is a test that fails for reasons unrelated to this codebase. The application code path under test (session cookie → `getCurrentUser()` → RLS claims) is identical for both providers, so the coverage loss is confined to the provider handshake itself. | rejected: mocking Google in e2e (tests the mock); skipping auth in e2e entirely (leaves every authorization check unverified).

## Reconciliation against LEGACY_INTELLIGENCE.md

_Added after the legacy forensic audit arrived mid-run. These decisions resolve conflicts between the audit (ground truth about what exists) and the master prompt (specification for what to build). Full conflict analysis in `docs/ANALYSIS.md` §7._

**[D-31] RLS is written for every table and verified by `db/rls_test.sql` as a Gate 1 blocker, not as a later hardening task.** | The audit is unambiguous: "no `rls` key exists in any entity file… there is no row-level isolation anywhere" — any authenticated user could read every order, every buyer phone number, and every seller's `exact_address` (a required field) straight through the SDK. This is the most serious defect in the system being replaced, so the replacement must prove it is fixed before anything is built on top of it. Making the RLS assertions a gate rather than a checklist item means a policy regression fails the build. | rejected: adding RLS in the hardening phase (the schema would already have consumers written against unrestricted access, and retrofitting policies under working code is how policies end up permissive); relying on the app layer (bypassed by service-role and by any direct access).

**[D-32] Delivery scheduling uses the legacy shift model — בוקר 09:00–12:00 / צהריים 12:00–16:00 / ערב 16:00–19:00 — with its calendar constraints: earliest tomorrow, no Saturdays, Friday mornings only, ≤90 days ahead.** | The master prompt asks for "date + 3-hour window", which the shifts satisfy. The constraints are hard-won operational knowledge: an interface that can offer a Saturday pickup in Israel is not slightly wrong, it is an appointment that will not be kept, and the cost lands on a crew that has already been dispatched. Reusing proven scheduling rules is strictly better than re-deriving them. | rejected: arbitrary 3-hour windows (loses the calendar constraints and offers slots crews don't run); free time entry (unschedulable against crew capacity).

**[D-33] Emailed action links are authenticated: a link like the legacy `/SellerResponse?orderId=…&action=approve` becomes a login-then-redirect into the seller's order page, never a one-click unauthenticated mutation.** | The legacy links let anyone holding the URL act as the seller — approving windows and advancing an order. Email URLs leak: forwarded threads, shared screenshots, mail-scanner prefetch, browser history on a shared machine. The convenience of one-click is not worth an unauthenticated state transition on someone else's transaction. | rejected: keeping one-click links (unauthenticated mutation of another party's order); signed single-use tokens in the URL (better, but still a bearer credential in an email body, and it adds a token lifecycle to maintain for a login the user needs anyway).

**[D-34] `payment_status` is NOT migrated from legacy; payment state is reconstructed from `payment_provider` + `payout_released_at`, and orders whose payment state cannot be reconstructed import as `cancelled`.** | 88 of 94 legacy orders carry `held_in_escrow` although no money was ever held, and `paid_at` is 0% filled even on the single genuinely paid order. Importing that column would write a false statement about money into a brand-new ledger on day one — and a ledger that starts out lying is worse than one that starts out empty. Defaulting the unreconstructable to `cancelled` is the conservative direction: it under-claims rather than inventing payments. | rejected: migrating the column as-is (encodes a known falsehood); mapping `held_in_escrow` → `paid` (asserts 88 payments that never happened).

**[D-35] The legacy import maps `pricing.display_price` → `listings.price_agorot`, never `pricing.requested_price`.** | Legacy sellers named a *net* price and the platform marked it up; v2 sellers name the *gross* price and the platform deducts. Mapping the net figure into a gross field would cut every imported listing's buyer-facing price by ~12% and cut the seller's proceeds by ~28% versus what they used to receive. Mapping the gross figure keeps buyer prices stable and seller economics close to whole. | rejected: mapping `requested_price` (silently repricing the entire catalogue downward); mapping `seller_desired_price` (the same problem, on an even more stale field).

**[D-36] The sell wizard displays a live "תקבלו: ₪X" payout figure beside the price input.** | The gross/net inversion (`[D-35]`) is invisible to a returning seller, who will type the number they always typed. A number they can see is the only reliable defence against a mental model they can't. This also serves new sellers, for whom "20% commission" is an abstraction until it is subtracted in front of them. | rejected: explaining the commission in help text (nobody reads it, and the failure mode is a seller who is surprised at payout time); showing it only at review (too late — the price is already anchored).

**[D-37] The admin KPI dashboard reports delivery revenue against delivery volume, broken down by zone and category.** | The v2 flat zone fees appear to sit below what the legacy distance/tier engine charged for the same jobs, on a catalogue that is 60% tier-4 sofas (ANALYSIS §7 C-2). The spec's fee schedule is followed as written, but a margin risk that is only visible in aggregate must be *made* visible, early and by default. A dashboard that shows GMV and take but hides delivery cost recovery would let this run for a year unnoticed. | rejected: silently following the spec (the risk is real and invisible); overriding the specified fees (not my call — it is a pricing decision with competitive consequences).

**[D-38] `PAYMENT_PROVIDER` accepts `mock | payplus | sumit`; the PayPlus skeleton is built exactly as specified and a Sumit skeleton is built alongside it.** | The master prompt specifies PayPlus, but the audit shows the business already operates on Sumit with a live key and one proven real charge, plus documented refund/authorize/capture/void endpoints. Building only PayPlus would hand Tom a go-live blocker (a new PSP relationship) to solve a problem he has already solved. The interface makes a second adapter nearly free, so both exist and the choice stays his. | rejected: PayPlus only (ignores a working payment relationship); Sumit only (disobeys an explicit spec instruction); making Sumit the default (the spec's default is `mock`, and defaults that reach for live money are wrong).

**[D-39] Verbatim legal copy is reused unchanged except for three factual corrections: the buyer-protection window (12h/24h → 48h in all three places it appears), and the privacy policy's list of payment processors (named third parties → provider-neutral wording).** | Published legal text should not be silently reworded — that is why the default is verbatim. But these two statements would be *false* about the v2 system: the Terms would understate the buyer's protection window relative to what the code grants, and the privacy policy would misstate which processor receives personal data. A privacy policy naming the wrong data recipient is a factual error about data flows, not a style choice. Corrections are marked in COPY.md so a lawyer can see exactly what moved and nothing else has. | rejected: verbatim including the errors (publishes false statements about rights and data flows); rewriting the legal copy wholesale (throws away careful, already-reviewed Hebrew and invites new errors).

**[D-40] The published ₪50 post-confirmation cancellation fee is implemented as `cancellation_fee_agorot` in `site_config`, defaulting to 5000, applied only to buyer-initiated cancellation after seller confirmation.** | Both the Terms and the Cancellation Policy publish this fee, and the legacy field existed but was never once charged — the classic gap between the contract and the system. Implementing it as config makes the running system match the published contract by default while leaving Tom a one-click path to the pilot's de-facto behaviour. Config rather than code is the point: it is what stops policy and implementation diverging again. | rejected: not implementing it (system contradicts its own published terms); hardcoding ₪50 (a policy change would need a deploy — exactly how the legacy contradictions arose).

**[D-41] The published "free resale within 7 days" promise is implemented via a nullable `commission_pct_override` on `listings` plus a resale action on delivered orders.** | The Buyer Protection page promises it in writing, and the legacy schema has the `resale_source_order_id` field to support it — it was designed and never finished. The implementation is genuinely small (one nullable column honoured by the pure fee engine, one pre-filled wizard entry point), and it is a strong retention mechanic for a marketplace whose binding constraint is supply: a buyer who doesn't love the sofa becomes next month's seller instead of a refund. | rejected: dropping the promise and editing the copy (removes a good mechanic and weakens a trust page); a full returns flow (out of scope, and the promise is explicitly resale, not return).

**[D-42] `legacy_redirects` keys on 24-character hex legacy ids as `text`, and the redirect middleware matches legacy paths case-insensitively.** | Legacy ids are Mongo ObjectId-shaped, not uuids, so a uuid column would reject every row. Legacy routing resolved both `/ItemDetails` and `/itemdetails` (React Router matched case-insensitively while the app's own helper emitted lowercase), so both casings exist in the wild — in already-sent emails and in whatever Google has indexed. Matching only one casing would 404 half the inbound links the redirect exists to save. | rejected: uuid column (wrong type); exact-case matching (drops real traffic).

**[D-43] Seller-confirmation rate and time-to-confirm are first-class KPIs, and a reminder job runs inside the confirmation window.** | 72% of all legacy orders died waiting for a seller to respond. That is not a rough edge, it is the business's central failure mode, and the master prompt's move from a 24h to a 48h window addresses the symptom rather than the cause. Reminders inside the window (legacy had the fields for this and never used them) plus one-tap authenticated confirmation are the levers; instrumenting the rate is what makes it possible to tell whether they worked. | rejected: relying on the longer window alone (doubles the wait before the same failure); no instrumentation (leaves the most important number in the business unmeasured).

**[D-44] Every `SECURITY DEFINER` function that mutates state is executable by `service_role` only, and the two RLS predicate helpers live in a non-API-exposed `private` schema.** | Found by Supabase's own security advisor after the first remote apply, and it was a serious hole: Postgres grants `EXECUTE` to `PUBLIC` by default, and Supabase publishes everything in `public` as an RPC endpoint — so `POST /rest/v1/rpc/transition_order` was reachable **anonymously**. Anyone could have moved any order to `completed`, or called `create_order` with an item price of zero. The whole point of routing state changes through a guarded function is defeated if the guarded function is itself a public endpoint, so the fix restores the intended shape: server actions call these through the service client having already checked authorization `[D-28]`. `is_admin()` and `owns_order()` must stay executable by `anon`/`authenticated` (RLS predicates are evaluated with the caller's privileges) and must stay `SECURITY DEFINER` (as `SECURITY INVOKER`, `is_admin()` reading `profiles` recurses through the profiles read policy that calls it), so they moved to `private` instead — reachable from RLS, absent from the REST surface. Verified: advisor goes from 20 warnings to 0, `anon` is refused `transition_order`, `anon` can still evaluate `is_admin()`, and `updated_at` triggers still fire after the revoke. | rejected: leaving them exposed and relying on the functions' internal checks (they had none — they were designed as internal); making them `SECURITY INVOKER` (breaks the definer-only writes and causes policy recursion on `profiles`); keeping the helpers in `public` and documenting the advisor warnings as benign (true today, but a later signature change silently re-inherits the exposure).

**[D-45] `pickup_street` is readable only by `service_role`; the API roles hold a column-level grant on every other column of `listings`, enumerated at migration time.** | Two mechanisms failed before this one worked, and the second failure was the serious one. First, `revoke select (pickup_street) … from anon` in the original RLS migration was **inert** — a table-level `GRANT SELECT` covers every column and a column-level revoke cannot subtract from it, so the address was never actually protected. Second, and worse: the table-level grant also covered `authenticated`, and since a signed-in buyer legitimately reads any *active* listing's row, **every signed-in user could read every seller's home address** — the same defect the legacy platform had, arriving by a different route. RLS is row-level and structurally cannot protect a column, so column privileges are the only mechanism. Enumerating the granted columns at migration time (rather than hardcoding a list) means a column added later is simply not granted, which fails closed. The address is now revealed only through server-side paths that check authorization first — the admin delivery manifest, and the buyer of a paid order. | rejected: relying on repository projections alone (one `select *` re-opens it, which is precisely the bug this defends against); a `SECURITY DEFINER` accessor function in `public` (would be an anonymous RPC endpoint — see `[D-44]`); moving the address to a separate table (cleaner in theory, but an extra join on every seller and admin read for a guarantee column privileges already give).

**[D-46] Public catalogue pages read through a dedicated cookie-free anonymous Supabase client whose fetches carry explicit Next cache tags; only personalised routes use the session-bound server client.** | Two separate mechanisms silently opt a route out of static generation, and hitting either one deletes the ISR strategy the whole SEO plan rests on. First, **any** component that reads cookies makes its entire route dynamic — so a session-aware site header in the root layout would have made every page in the product dynamic, including `/`, `/catalog` and every item page. Second, supabase-js calls `fetch` internally and Next's `fetch` defaults to `no-store`, which also forces dynamic rendering — so even after removing cookies, `/` still rendered on demand until the client passed explicit `next: { revalidate, tags }`. Both were caught by reading the build output rather than by anything failing. Reading as `anon` is not a compromise here: RLS then returns exactly what an anonymous visitor may see, which is precisely the correct visibility for a cacheable public page, and the tags are the same ones the on-demand `revalidateTag` map needs. Session state moved to a small client component (`AuthChip`), which costs one render's worth of a reserved-width placeholder. | rejected: session-aware header rendered on the server (makes the entire site dynamic — the single most expensive mistake available in this architecture); `export const dynamic = 'force-static'` (masks the cookie access rather than removing it, and breaks the routes that genuinely need a session); enabling PPR (would work, but it is an experimental flag to depend on for a property that a clean client boundary already gives).

**[D-47] Every Supabase read destructures `error` and throws it; notification sending is the one deliberate exception, catching everything at its own boundary.** | `const { data } = await supabase…` turns an API failure into an empty array, and an empty array is a perfectly plausible-looking UI state — so a broken query renders as "no results" against a database that visibly contains the rows. This cost real debugging time twice: a two-way foreign key needing an `!hint` presented as an empty catalogue, and a stale PostgREST schema cache presented as an empty review queue. The rule is now uniform across `src/app/**`, `src/lib/db/**`, `src/lib/actions/**` and `src/lib/jobs/**`, and it matters most in the jobs: a cron that silently processes zero orders because its query failed reports success while refunds quietly stop happening — exactly how the legacy reservation cleaner died. Notifications invert the rule because they are always called *after* a state change has committed: a failed email must not make a completed payout look like a failed one, so `send()` never throws, records the failure to `outbound_events`, and returns `false`. | rejected: leaving reads unchecked (the failure mode is invisible by construction); a wrapper that returns a Result type (a larger refactor for the same guarantee `throw` already gives inside RSC and server actions); letting notification failures propagate (turns a delivery problem into a false operational error and invites retrying settled work).

**[D-48] Playwright never asserts on formatted currency, and never hardcodes a delivery shift.** | Both are cases of a test encoding an assumption the product does not hold. `Intl` renders ILS in `he-IL` as `‏800 ‏₪` — trailing symbol, non-breaking space, two RLM marks — so a locator filtering on `"₪800"` matches nothing, forever, for reasons invisible in the diff; money-bearing rows therefore carry a `data-order-id` and tests key off that. Separately, shift availability is a function of the weekday (Friday is morning-only, Saturday has no service at all), so a spec naming `'evening'` passes or fails depending on which day the suite runs — the specs now select from the options the page actually offers. | rejected: normalising the formatted string in tests (couples every assertion to ICU's output and would silently rot on a version bump); freezing the suite's clock to a fixed weekday (hides genuine weekday-dependent bugs, and the scheduling rules are exactly the thing worth exercising).

**[D-49] The sitemap is served by hand-written route handlers rather than Next's `sitemap.ts` metadata convention, and the index lives at `/sitemap.xml`.** | The convention has no index form. Adding `generateSitemaps` — which the 50,000-URL protocol limit makes necessary once programmatic category × city pages multiply — silently relocates the output to `/sitemap/<id>.xml` and leaves `/sitemap.xml` returning a 404. That is the single URL robots.txt points at, Search Console defaults to, and every crawler tries first, and nothing in the application ever requests it, so the failure is invisible until organic traffic doesn't arrive. Route handlers cost about forty lines of XML rendering and put the URL shape under our control; the rendering itself sits in an import-free module so the chunking maths is unit tested rather than eyeballed. | rejected: a single un-chunked `sitemap.ts` (works today, and silently truncates the day the catalogue passes 50,000 URLs — the failure mode is losing the tail of the index with no error); keeping `generateSitemaps` and pointing robots.txt at `/sitemap/0.xml` (leaks an implementation detail into a published URL and still 404s the path everyone actually tries).

**[D-50] `clay`, `warning`, `success`, `ink-muted` and `ink-subtle` were darkened until every one clears WCAG AA against every background it is used on.** | The original palette failed in the two places it mattered most: `clay` at `#C4633F` gives 3.78:1 on canvas and 4.04:1 for white-on-clay, so the price and the primary CTA — the two elements the accent exists for — were both below AA. `warning` and `ink-subtle` were at 3.03:1. Each correction is a uniform scale toward black, which preserves hue exactly, so the palette reads the same and passes; the design skill now carries the requirement and the check that catches it. `ink-subtle` could not simply be darkened to passing without colliding with `ink-muted`, so `ink-muted` moved down too and the three-step text scale kept its spacing. | rejected: leaving the palette and marking the failures "brand colours" (it is a legal requirement in Israel, and the accessibility statement this product publishes promises AA specifically); using AA-large thresholds for the price (it renders at 22px semibold, which axe measures as normal text, so the exemption does not actually apply).

**[D-51] `tailwind-merge` is configured with the project's custom type scale.** | `cn('bg-clay text-white', 'text-body-sm')` was silently dropping `text-white`. tailwind-merge resolves conflicts by class group and classifies unknown `text-*` utilities by guessing; `text-body-sm` is a font size that looks exactly like a colour, so it was treated as conflicting and the colour lost. Every primary and danger button on the site rendered ink text on clay instead of white — through two phases, in the most-clicked element in the product, invisible because dark-on-clay is legible enough not to look broken. Only a contrast audit found it. Registering the scale makes size and colour distinct groups again. | rejected: dropping `cn()` and concatenating classes (loses conflict resolution everywhere, which is the reason to have it); renaming the scale to `text-size-*` (a larger, more invasive change that leaves the same trap set for the next custom utility).

**[D-52] `npm run db:reset` truncates the application tables, re-seeds, and clears the Next fetch cache — refusing to run against any non-local database.** | Two problems, one script. First, the e2e suite creates listings, orders and payouts on every run, and after enough runs they outnumber the seed: 113 of 165 listings were `פריט בדיקה` fixtures, the catalogue was full of them, `generateStaticParams` prerendered every one, and an audit of "the item page" was really an audit of a fixture with no photos behind it. Second, `next build` reuses `.next/cache/fetch-cache`, so a build immediately after a data reset prerenders the *previous* catalogue — pages for listings that no longer exist, with 404ing images — and reports success. The host check is not paranoia: this deletes every order and payout, and the same command in the wrong shell is how a production database dies. | rejected: cleaning up in test teardown (leaves nothing to inspect after a failure, which is when the rows are most useful); accepting the drift (it silently degrades every audit run against local data, which is every audit run).

**[D-53] Rate limits are counted in a Postgres table, applied to five actions, and fail open.** | An in-process counter is the obvious implementation and is worthless here: the application runs as serverless functions, so the count is per-instance and resets on every cold start — it passes review and limits almost nothing. One shared table is the only place the number is true. The five protected actions are the ones where volume costs real money or real attention: the metered AI call, offers (the cheapest way to harass a seller), disputes (a human process on our side), listing submission (a human review queue), and checkout (which reserves stock). Failing open is deliberate: a limiter that takes checkout down when the database hiccups has done more damage than the abuse it was guarding against, so the error is logged and the request proceeds. A fixed window rather than sliding, because it is one atomic upsert and the worst case — 2× the limit across a boundary — does not matter for any of these. | rejected: an in-memory LRU (per-instance, resets constantly); Upstash or another external limiter (a new vendor, a new failure mode, and a new secret, for a table and one function); failing closed (converts an infrastructure blip into lost orders).

**[D-54] The CSP is not nonce-based, and both `upgrade-insecure-requests` and HSTS are keyed on the site's own scheme rather than `NODE_ENV`.** | A per-request nonce has to be generated in middleware and injected into the HTML, which forces every page to render dynamically — and static rendering is the one property the entire SEO strategy rests on `[D-46]`. So the policy keeps `'unsafe-inline'` for scripts, which Next's own bootstrap requires anyway, and is strict about everything that does not need a nonce: `frame-ancestors`, `object-src`, `base-uri`, `form-action`, `img-src`, `connect-src`. Those block real attack classes; a nonce would mainly defend against injected inline script, which the app has no vector for. Keying the two https-only headers on `NEXT_PUBLIC_SITE_URL`'s protocol rather than `NODE_ENV` is not pedantry: `next start` runs with `NODE_ENV=production` locally too, and over http `upgrade-insecure-requests` rewrote every call to the local Supabase into https and silently broke sign-in and favourites, while HSTS would pin the browser to https for a hostname with no certificate for two years. | rejected: a nonce-based CSP (deletes ISR sitewide); no CSP at all (leaves clickjacking, `<base>` hijacking and form exfiltration unaddressed for no gain); report-only (a policy nobody enforces is a policy nobody fixes).

**[D-55] Routes that can call `notFound()` have no route-level `loading.tsx`.** | A loading file opens a Suspense boundary around the whole page, so Next begins streaming and commits the status to 200 — after which `notFound()` can only inject a `noindex` meta tag. The result is a soft 404: it renders the right page, reports success, and gets indexed as real content. Adding skeletons to the slug routes produced exactly that on four routes at once, and nothing failed. Those routes are prerendered anyway, so the only request that would ever see a skeleton is an unknown slug — precisely the request that needs a real 404. `/catalog`, `/dashboard` and `/admin` keep theirs: they render an empty state or redirect and never call `notFound()`. | rejected: keeping the skeletons and accepting soft 404s (indexes not-found pages as content and wastes crawl budget); moving the existence check above a narrower internal Suspense boundary (correct, and worth doing if one of these routes ever needs streaming — but it is more moving parts than an already-prerendered page needs today).

**[D-56] Every RLS predicate wraps `auth.uid()` and the `private` helpers in a subselect, and admin policies are scoped to writes.** | Supabase's performance advisor flagged 31 warnings, all on the hottest read path in the product. Two causes. A bare `auth.uid()` inside a policy is re-evaluated **per row**; `(select auth.uid())` is hoisted into an InitPlan and evaluated once per query — on a catalogue scan that is one function call instead of one per listing. Separately, every table carried a user-facing SELECT policy *and* an admin `for all` policy, and Postgres evaluates every permissive policy for every row and ORs them — so the admin policy doubled the work on every read while contributing nothing, because each read policy already admitted admins. Scoping admin to `insert`/`update`/`delete` costs three policy objects where there was one, and only ever evaluates one of them per statement. `listings` additionally had two permissive SELECT policies for `authenticated` (public statuses, own listings) which are now one predicate; `anon` keeps a separate policy because it must never see a draft. Result: `auth_rls_initplan` 15 → 0, `multiple_permissive_policies` 16 → 0, with `db/rls_test.sql` proving the permission set is byte-for-byte unchanged. | rejected: leaving it (a per-row function call on the product's most-read table, growing linearly with the catalogue); merging admin into the read policies with `or private.is_admin()` and dropping the admin policy entirely (would have silently removed admin *write* access); adding an index for each of the seven unindexed foreign keys the advisor also lists (four have no query behind them, and an index nobody reads still costs every write).

**[D-57] Categories, brands and delivery zones ship as a migration (`0024`), not only as seed data, and the remote's rows were corrected in place rather than replaced.** | Two separate calls. First, *where reference data lives*: the operator's assistant had to insert the taxonomy by hand because nothing but `db/seed.ts` created it, and `db/seed.ts` also creates forty fictional listings and three accounts with a known password — so there was no way to populate a production taxonomy without also populating fake inventory. Shipping it as a migration follows the precedent `0013` already set for `site_config` and makes a freshly migrated database immediately usable; the seed upserts the same rows, so the two agree rather than compete. Second, *how to fix rows that already exist*: seven slugs on the remote disagreed with the application's routing (`closets-storage` vs `storage`, `outdoor` vs `garden`, `shelves-bookcases` vs `shelves`, `home-center` vs `homecenter`, `rahitei-doron` vs `rahitey-doron`, `shomrat-hazorea` vs `shemerat-hazorea`, and `sealy` on a row named סילון — a different company entirely). Deleting and reinserting would have been simpler to write and would have discarded rows a human created; correcting in place, matched on the Hebrew name, keeps their ids and their provenance. The operator's one extra city, רחובות, is preserved and has been adopted into `db/seed-data.ts` so the canonical seed now matches the service area actually being offered. | rejected: leaving reference data seed-only (guarantees the next operator repeats the hand-insert, and there is no safe way to run the seed against production); delete-and-reinsert (loses ids and treats the operator's work as disposable — and would have to be re-decided the moment a listing references a category); treating the remote as canonical and changing the application's slugs to match (the slugs are already in `db/seed-data.ts`, in the listing fixtures, and in the brand transliteration dictionary, so the blast radius is far larger and `sealy` would have stayed wrong).

**[D-58] The remote's function bodies are kept byte-identical to the repository, comments included, and a migration is spent on that alone.** | Three functions — `transition_listing`, `transition_order`, `consume_rate_limit` — had been applied to the remote by hand during the build and retyped without their comments. The programs were provably identical: hashing each body with `--` comments stripped and whitespace collapsed matched across all thirteen functions. So this buys nothing at runtime. It is still worth `0023`, for two reasons. `transition_order` is the order state machine, and the comments that had gone missing are exactly the ones recording why the row lock is there, why a same-status transition is still written to the audit, and why every timestamp is set in one statement — someone reading `\sf transition_order` on production was getting the code with none of the reasoning that makes it safe to change. And it takes the object-level diff between repo and remote to **zero**, so the next person to run that diff gets a clean result instead of six lines they have to re-derive as benign. A reconciliation that leaves permanent expected noise is one nobody runs twice. | rejected: documenting the difference and leaving it (permanent noise in every future diff, and the production copy stays unexplained); syncing the repo down to the remote's comment-free version (throws away the reasoning to make a diff quiet — backwards).

**[D-59] Schema equivalence between repository and remote is asserted by an object-level diff, kept in the repo as `db/introspect.sql`.** | "The migrations are applied, so the schema matches" is an inference, and this run showed it can be wrong in ways that matter — the same file count hid a differing ledger, and identical ledgers would still have hidden the comment divergence. Counting files proves nothing about objects. The introspection emits one line per object across nine categories — tables, columns with type/nullability/default, constraints, indexes, enums, functions with body hash and security mode, policies with their `using` and `with check` expressions, the RLS flag, triggers, and the table, column and function grants held by `anon`, `authenticated` and `service_role` — sorted, so the same text run on both sides diffs line by line. The grant categories are there deliberately: `[D-44]` and `[D-45]` were both privilege bugs invisible in any schema dump that stops at DDL. | rejected: `supabase db diff` (needs Docker, unavailable here, and its output is a migration rather than an inventory); `pg_dump --schema-only` (misses grants and column privileges, which is where two of this project's three worst defects lived); trusting the migration ledger (it records what ran, not what resulted).

**[D-60] An end-to-end assertion on a multi-write action polls the terminal state as a whole, never one field of it.** | `markInspectionFailed` writes the cancellation, then calls the payment provider, then records the event, then writes `refund_agorot` — four statements and one network round trip apart. The spec polled the status with `toPass` and read the refund amount immediately after it returned, so it was asserting on a row it had proved was only *partway* through the action: the refund read 0 whenever those four statements did not finish inside one poll interval. It passed twice and failed on the third run, and the failure — `Expected: 64900, Received: 0` on a cancelled order — looks exactly like a product bug that refuses to refund, which is the expensive part. Folding `refund_agorot` and the listing release into the same `toPass` makes the poll wait for the state the test is actually about. This is the second instance of the shape in this suite, after the payout `data-status` race in Phase 4, so the rule is now general: if an action writes N things, the assertion waits for all N. | rejected: raising the timeout (does not help — the test was not waiting for the refund at all, it was waiting for something else and then reading the refund once); a fixed sleep after the status poll (turns a race into a slower race, and picks a number with nothing behind it); reordering `src/lib/actions/admin.ts` to write the refund amount first (writing a refund before the provider confirms it is a worse invariant than a flaky test, and the order there is deliberate); marking the test `retries: 1` locally (the config states a flaky test is a broken test, and retries would have hidden this rather than surfaced it).

## Run 2 — governance, gates and product remainders

**[D-61] Governance is five artifacts, and `CLAUDE.md` is the only one an agent may not edit.** | Run 1 found thirteen defects during the build because a human read every diff. That does not survive operation by sessions that share no memory and each believe themselves the first, so the layer exists to answer "what stops the fifteenth session from undoing what the first one proved". Splitting it into five files rather than one is load-bearing, not tidiness: the sole-author clause needs a file the operator alone owns, and a `PreToolUse` hook needs one unambiguous path to block. Mixing an operator-only constitution with an agent-amendable policy in a single document makes that boundary unenforceable. Each gate in `ADR-001` is anchored to a defect class that actually happened here — soft-404, contrast, seed drift, migration-count drift — and the anchoring is itself the rule: a gate that cannot name the failure it prevents is a candidate for deletion at the next review. | rejected: copying `gt-factory-os-production-brain` verbatim (its invariants protect inventory truth and its L5 list is about stock mutations; imported unchanged they would be rules nobody could anchor to a Restyle defect, which is the ceremony this ADR warns against); relying on `docs/DECISIONS.md` alone (60 excellent entries that are a *history*, not a *policy* — a session can read all of them and still not know whether it may merge); operator code review (what Run 1 did, it worked, and it does not survive the operator being unavailable — which is the case the kill switch exists for); branch protection and CI only (CI can prove tests pass; it cannot express "money is agorot" or "never switch the payment provider", and those are the rules that matter most); a single combined `GOVERNANCE.md` (see above).

**[D-62] The kill switch is checked once in `runJob`, reads both a file and an environment variable, and a halted job returns HTTP 200.** | Three choices. *Once, in `runJob`*: all seven cron jobs route through it, so seven per-job checks would be seven places to forget the eighth. It runs before any query, transition or refund — halting has to mean nothing happened. *Both mechanisms*: the file is greppable, reviewable, and `git log` says who stopped what and when; but on Vercel the filesystem is a build artifact, so creating a file there needs a deploy, and needing a deploy to stop runaway automation defeats the purpose. The variable takes effect on the next invocation. *200, not 5xx*: the job did exactly what it was told, and a failure status would make Vercel Cron retry the very automation the operator just stopped. The test proves the halt for all seven jobs by running them with **no Supabase configured** — if the guard did not fire first, each would throw on the missing environment, so a clean halt is proof nothing downstream ran; the inverse case is asserted too, so an unconditional guard cannot pass as a working one. | rejected: an environment variable alone (invisible in the repository, no history of who set it); a `site_config` row (the switch must work when the database is the thing misbehaving); a per-job check (see above); returning 503 (Vercel retries it).

**[D-63] The release gate reports three statuses, and a `skipped` stage is never counted as a pass.** | The verdict is `pass` only when every stage passed; skips alone still produce `fail`. This is the direct lesson of `[D-49]` and `[D-51]`: in both cases a check that quietly did nothing was read as green, and in both cases the product shipped broken for weeks. A binary pass/fail forces the opposite mistake — a stage that cannot run in this environment either fails the build for an environment reason, which trains people to ignore red, or is quietly counted as green, which is how this project got here. The third status keeps the "could not run" case loud and carries its reason into the scorecard. `ALLOWED_SKIPS` then defines the narrow set of reasons under which CI may have covered the stage instead, and eligibility for L2 additionally requires CI to have run it on the same commit. An exception thrown by a stage is a `fail`, never a `skip` — fail-closed at its most literal. | rejected: binary pass/fail (see above); treating skips as passes when a flag is set (a flag that turns a gate green is a gate nobody trusts); requiring every stage everywhere (unrunnable — no environment has a browser, a writable Supabase, a seeded reference database and Lighthouse simultaneously without becoming CI).

**[D-64] Gate stages read expected status and indexability from each page's own source rather than from a maintained list.** | The route auditor needs to know that `/sell/new` should 307 (it calls `requireUser`) and that `/sell/new/submitted` is `noindex`. Encoding those as exceptions in the gate creates a second copy of a fact the page already states — and the second copy rots: the next auth-gated page becomes a spurious gate failure, and worse, a page that *stops* redirecting is never noticed because the list still says it should. Reading `require(User|Admin|…)` and `robots: { index: false }` out of the source means the page and the audit cannot disagree. The same reasoning stops one step short for hub thresholds: brand and category×city hubs enter the sitemap above `MIN_ITEMS_FOR_HUB` and go `noindex` below it, and that rule is owned by `src/lib/seo/sitemap-data.ts` — so the gate audits those routes for status and treats the sitemap as the authority on membership rather than re-deriving the threshold. | rejected: a hardcoded exception list (rots in both directions, as above); asserting only 2xx-or-3xx (accepts a 404 as a redirect and gives up the whole soft-404 class); running the audit authenticated (then it never checks that the gate redirects at all).

**[D-65] The gate's e2e stage refuses any Supabase target that is not localhost.** | The suite signs up buyers, sellers and an admin, creates listings, and drives orders through to payout and refund. Pointed at the production project it would do all of that for real. The guard is therefore not "can this run here" but "are we allowed to write to this target", and only a localhost origin qualifies; CI supplies one with `supabase start`. Stated as a skip with the target named, so the reason is visible in the scorecard rather than being an unexplained gap. | rejected: an opt-in `--allow-remote-e2e` flag (a flag whose only purpose is to let money-moving tests run against production is a flag that will eventually be passed by accident); read-only e2e against production (over half the assertions are about state transitions, so what remained would not be the suite); trusting the runner to point it correctly (the failure mode is silent and irreversible).

**[D-66] `lighthouse` and `@axe-core/playwright` are added as devDependencies; the gate's `.env` reader is fifteen lines of local code.** | Two dependency calls in opposite directions, both from the `restyle-yagni` ladder. Lighthouse and axe are *measurement instruments*: re-implementing WCAG rule coverage or Core Web Vitals scoring is not a few lines, and a hand-rolled approximation would produce numbers nobody could compare against an industry baseline — the point of the budgets is that they mean what everyone else means. They are devDependencies, so they never reach the bundle. The `.env` reader goes the other way: `dotenv` would be a runtime dependency for fifteen lines of parsing that has one requirement worth stating — an existing process variable always wins, so CI secrets are never overwritten by a stray file. Rung 7 of the ladder says one line before fifty; here it says fifteen lines before a dependency. | rejected: hand-rolling contrast-only a11y checks instead of axe (covers one rule class out of dozens, and this project's a11y history is not limited to contrast); running Lighthouse as a hosted CI action only (the local loop is where a regression should be caught, not the PR); `dotenv` (a dependency for a parser, with precedence semantics we would have to check anyway).
